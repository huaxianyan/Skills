# 仓库交接记录

`https://github.com/huaxianyan/skills`，公开仓库，默认分支 `main`。

跨项目复用的 Agent Skills 合集。2026-09-25 建，初始两个技能；2026-09-28 加第三个并升级第一个。2026-10-13 加第六个。

这份文件是仓库的交接记忆，跟代码一起提交。本机专用的信息（git 身份、命令行为差异）放在不进库的 `AGENTS.md`。

## 一、定位与边界

- 只收**跨项目通用**的规范。项目专属的东西（构建命令、包名、证书指纹、安装方式）一律不进，留在各仓库自己的发布技能或项目约定里。
- 每个技能自包含：`SKILL.md` 加可选的 `references/` 与 `scripts/`，脚本只用标准库。不依赖外部工具（例如不依赖 `autocorrect`），因为用法就是「给个地址，克隆后直接用」。
- frontmatter 只写 `name` 与 `description`，不写 `agent_created` 这类本地字段，其他支持 Agent Skills 的工具也能直接用。

## 二、六个技能

- `chinese-tech-writing`：中文技术文案与排版规范。2026-09-28 与某次全局版本的 `chinese-copywriting` 合并升级。句子与结构来自阮一峰，排版来自《中文文案排版指北》，补上「默认行文风格」与「语气与行文」两节。脚本从两个变三个：`check_style.py`（启发式）、`check_clauses.py`（句长）、`check_typography.py`（确定性硬规则，可接 CI）。
- `project-conventions`：2026-09-28 新增，2026-09-29 扩充。凭据与 SSH 私钥底线、项目约定文件写法、开发进度文档、任务预期与超时纪律、测试临时产物清理。带 `references/handoff-template.md`。
- `release-notes-standard`：发布说明与 Release 页面规范。2026-10-11 起要求新功能与问题修复分节；2026-10-12 补充产物命名（`<项目名>-<架构>-<版本号>.apk` 加同名 `.sha256`）与构建信息表字段。带 `verify_release_notes.py` 与 `references/retrofit-history.md`（历史 Release 追溯流程）。
- `android-modern-standards`：2026-10-11 新增，2026-10-12 补充 target SDK 节奏。Android 现代开发规范，三条主线：平台新特性尽量接入（edge-to-edge、预测性返回、大屏可调整）、界面优先用原生 Material 3、动效以项目指定的样板应用（Pixel Text）为参照。版本号都带核对日期，判据与做法不带。后补：以主力设备系统升级为提升 `targetSdk` 的节奏、第一轮只提数字不加兼容补丁、逐级验收与归因、`targetSdk` 只写纯整数而次版本号只在编译侧。
- `experience-curation`：新增开发经验整理的保守提议规则。开发任务收尾时判断候选，优先更新已有技能，每个任务最多询问一次，确认后才整理。
- `readme-standard`：2026-10-13 新增。README 撰写标准，管仓库门面的结构与边界。九节顺序（图标与标题、定位语、截图、特性、快速开始、使用与配置、设计与实现、文档、许可证），可省略但不乱序。另定内容边界与分工表、快速开始的命令写法。带 `references/skeleton.md` 骨架模板。首版不带门禁脚本，见下方决策一节。

## 三、定下来的决策

### 文案规范

- **引号默认直角引号**（2026-09-28 改）。此前仓库默认弯引号、全局默认直角引号，两处冲突。依据是两个相关公开仓库的实际用法：一个 3783 处留空格、12 处紧贴，另一个全用 `「」` 且零弯引号。少数历史项目用弯引号时，按项目约定覆盖，脚本传 `--quotes any`。
- **中文与行内代码之间留空格**（2026-09-28 改）。仓库原来写「不加空格」，全局写「留空格」，已有项目的门禁脚本也强制留空格，实际用法同样是留空格。统一为留空格。
- **自带扫描脚本，不依赖 autocorrect**。开发机上没装这个工具，而且自带脚本的判据能按项目口径改。
- **扫描脚本要有降噪规则**。引号与行内代码里的内容不参与判定，反例行跳过，表格行不参与句长统计，代码文件只看注释行。没有这些规则，扫规范文件自己会报出上百条噪音（规范里本来就列着那些词）。写规范文档时，词表要用引号包住。2026-09-28 又补两条：破折号总数与弯引号检查都要先剥行内代码，`check_typography.py` 还要剥掉引号里的内容，否则规则自己的示例会被当成问题。
- **两个排版脚本分工**（2026-09-28 定）。`check_style.py` 管需要人看的启发式项（长句、AI 腔、破折号密度），`check_typography.py` 只判确定性排版并能当 CI 门禁。合成一个会让门禁跟着启发式规则抖。

### Android 规范

- **提升 target 的节奏跟主力设备的系统版本**（2026-10-12 加）。设备升级到大版本就是提升 `targetSdk` 的时机，不等应用商店的下限提醒。依据是验收方式：ART 加载、native loader、按键音、内存上限、输入法可见性这类行为变更只能靠真机判断，设备不升级就没有可验证的环境。应用商店的 `targetSdk` 要求是下限，不是目标。
- **第一轮只提数字，不加猜测性兼容补丁**（2026-10-12 定）。先让新版行为自己暴露问题，再针对真实故障修。预先加补丁会掩盖真问题。
- **逐级推进，每级留验收点**（2026-10-12 定）。从 target 26 追到 36 这类跨度要一级一级来，每级单独记录触发了什么问题、怎么修、真机结论。一次跳多级会把归因混在一起，出问题时说不清是哪一级引入的。
- **`targetSdk` 只写纯整数**（2026-10-12 按本机构件核对）。API 37 起平台目录带次版本号（`android-37.2`），但次版本号只能出现在编译侧：清单的 `targetSdkVersion` 只定义整数属性，AGP 侧用 `compileSdkMinor`。设备侧的次版本号与本机平台可以不一致（设备 `37.1`、平台 `37.2`），不影响写法。
- **比较 `targetSdkVersion` 先解析再比较**（2026-10-12 定）。枚举已知取值会在下次提升 target 时静默失效，这条来自项目构建文档的实测经验。
- **新建独立技能，不塞进现有技能**（2026-10-11 定）。Android 规范与「项目约定」「中文文案」「发布说明」三件事都不同类，受众也不同（写 Android 代码时才用得上）。塞进去会让触发词变浑。
- **判据与版本号分开写**（2026-10-11 定）。版本号、依赖坐标、API 状态都带「2026-10-11 核对」这类日期，判据与做法不带日期。Android 一年一个大版本，半年后前者必错、后者仍对。写清核对日期才能让人知道哪些要重新查。
- **内容从真实返工记录提炼，不从文档直接抄**（2026-10-11 定）。预测性返回一节的手势进度转场、不透明分层、迁移名单单一定义点，都来自一个真实项目在 API 36 上的三轮返工。抄一遍官方概述没有价值，官方文档已经写得更清楚。
- **写明「不用什么」比「用什么」更有用**（2026-10-11 定）。常见错误一节列的是实测踩过的：只设透明不处理 insets、进度分支里复用交叉淡化、同时维护两份接入名单、把 alpha 当长期基线。这些在官方文档里不会以「错误」形式出现。
- **与项目约定文件划清边界**（2026-10-11 定）。具体版本号、依赖坐标、设备与调试信息写进项目的 `AGENTS.md` 或构建文件，不写死在技能里。项目已定的技术选型优先于技能的一般建议。

### 发布说明规范

- **产物命名带项目信息**（2026-10-12 加）。格式 `<项目名>-<架构>-<版本号>.apk`，同名 `.sha256` 里带产物文件名。理由：`app-release.apk` 这类默认名无法分辨项目与版本，下载到本地会互相覆盖，多 ABI 时还会重名。
- **`gh` 的 `#` 不是重命名**（2026-10-12 核实）。按 `gh` 2.96.0 源码（`pkg/cmd/release/shared/upload.go` 里 `Name: fi.Name()`），资产名取自磁盘文件名，`#` 只设置显示标签（`label`）。本项目发布工作流里的 `"$APK_PATH#$RELEASE_APK_NAME"` 写法之所以看着「对」，是因为 `APK_PATH` 本来就已经叫 `RELEASE_APK_NAME`，那个 `#` 是多余的。要规范名字得先让文件本身是那个名字。
- **校验清单格式与 `sha256sum` 生成格式不同**（2026-10-12 核实）。项目写的是 `SHA-256  <哈希>  <文件名>`，而 `sha256sum` 生成的是 `<哈希>  <文件名>`。coreutils 的 `-c` 只接受本程序输出过的行（BSD 风格要用 `--tag`，也不是这个写法），所以项目那种写法直接给 `sha256sum -c` 会报格式错误。规范里两种都写了，但要写清区别，不宣称「能直接 `-c` 校验」。
- **构建信息表要能回答三个问题**（2026-10-12 定）。能不能装（架构、min / target SDK）、会不会替换现有包（包名）、能否覆盖升级（签名证书指纹）。签名证书与源码提交两项不能省。
- **新功能与问题修复分节描述**（2026-10-11 改）。用 `## 新功能` 与 `## 问题修复` 区分新增能力和原有缺陷的修复。至少出现一节，每个分类节必须有更新列表条目。代码块中的示例不算，分类准确性仍需人工审阅。
- **不强制两节都写**（2026-10-11 定）。纯修复版本只写修复，纯功能版本只写新功能。不把其他改进或内部重构硬归为 bug 修复。
- **存量 Release 不强制回溯**（2026-10-11 定）。新版本采用新格式。主动回填历史时按当时的提交和详细记录分类，不用自定义节名参数绕过分类要求。本轮未改其他项目或线上 Release。
- **门禁接入需同步迁移**（2026-10-11 定）。`--summary-heading` 已移除。更新脚本时同步调整 CI 参数和新版本说明，未安排回填的历史文件不纳入新格式检查。英文项目可用 `--feature-heading` 与 `--fix-heading` 追加节名。
- **发布资产不设显示标签**（2026-10-20 加）。`#` 设的 `label` 在页面上盖住文件名，文件名退到次一级位置：同一项目每个版本都标成「Android APK」，列表里分不出哪个文件是哪个版本，下载到本地还得改名。`gh release create <tag> dist/*` 不带 `#` 就不会有标签；存量标签用 `gh api -X PATCH .../assets/<id> -f label=` 清掉。触发这条规则的是一个 Android 项目：五个历史 Release 的 APK 都带 `Android APK` 标签，文件名本身早已规范。
- **门禁脚本参数化**。目录、行数上限、链接正则、禁用节都能用命令行覆盖。这样用 CHANGELOG 风格的项目能共用同一个脚本，只换 `--link-pattern`。

### 项目规范

- **`project-conventions` 最初收的五件事**（2026-09-29 定）。私钥只能直接用、项目约定文件该记什么、进度文档当交接记忆、任务要有预期时长、测试临时产物用完就清。都是跨项目成立、每个新仓库都要重新交代一遍的东西。
- **真机是用户的设备，不是测试夹具**（2026-10-20 定）。重启、关机、卸载、`pm clear`、改系统状态一律先问，授权只对当次有效；`adb install -r` 因签名不符或版本号未递增而失败时，报错误码与可选路径，不自己 `adb uninstall` 再全新安装。出处是启动器项目上真实发生的两次越界：为验证一遍重启了真机；安装失败后擅自卸载重装，清掉了用户攒的配置。
- **临时产物清理限于本轮自己生成的文件**（2026-09-29 定）。不许用宽泛通配符删目录或缓存，区分不了来源时先问。判定标准只有一条：有人会再次用到的才当资产留下并入库，其余按临时处理删掉。
- **接手项目前先查跨项目档案**（2026-10-20 定）。动机：每次开新会话都要用户交代一遍去查旧记录，忘了就会出现「这个也不知道那个也不知道」。分两层：本机 Pi 通用指引（`~/.pi/agent/AGENTS.md`）只放常驻动作与指针，查询顺序、对接动作与建档规则写在 `project-conventions` 的「接手项目先查已有记录」一节。档案仓库的具体路径只写在常驻指引里，技能是公开的，用占位符。
- **GitHub 的仓库操作走 SSH，`gh` 只用于 API**（2026-10-20 定）。克隆、拉取、推送、推标签一律 `git` 加 `git@github.com:<owner>/<repo>.git`，私钥放在 `~/.ssh`；Release 与资产、Actions、Secrets、PR 与 Issue 这类只有 API 才有的事才用 `gh`。动机：最近开新项目时，助手一要连 GitHub 就默认调 `gh`，用户得每次交代一遍。私钥的读取禁令不变。
- **开发进度文档必须进仓库**（2026-09-28 定）。放仓库目录、跟代码一起提交，**不放 `.pi/`、`.claude/`、`.workbuddy/` 这类助手私有目录**，不为某个软件做特化。换了工具就没人看得到，那不是交接。私有目录只允许放临时草稿。这条带出一个后果：进度文档是公开的，而项目约定文件是不入库的，两者可见性相反。所以进度文档里不能写内网地址、服务器路径、设备序列号、凭据位置与口令，需要指向时只写「见本机 `AGENTS.md`」。技能里做了一张对照表把两份文件的边界钉死。

### 经验整理提议

- **先用轻量规则试行**。用户选择保守方案，新增 `experience-curation`。候选需已确认、可复用且边界明确，还需重复返工、明确长期要求或已查清的高代价事故作为强信号。
- **收尾时提议，每个任务最多一次**。无合格候选正常结束。拒绝后不追问，推迟后等用户主动回来。优先补充已有规范，确认后才写入。
- **启动指引与正文分离**。常驻规则只引用技能，详细判断规则集中在技能里。本机 Pi 已配置加载指引，不改其他工具。
- **能力边界明确**。这是提示词约定，没有后台扫描、候选数据库或严格的跨会话去重。先试行约 10 个任务，不为统计额外保存会话。

### README 规范

- **新建独立技能，与 chinese-tech-writing 分工而非互相覆盖**（2026-10-13 定）。readme-standard 管结构与边界（梗概、框架、节顺序、内容放哪），遣词造句仍归 chinese-tech-writing。两个技能不互斥，readme-standard 里写明分工。不改 chinese-tech-writing 的描述与触发词。
- **截图区包裹居中流排，不进表格不逐图配说明**（2026-10-13 定，同日三次收紧）。用户先否掉某现有项目一图一段解释的 HTML 表格。再否掉两栏表格替代方案。再否掉逐张独立成段的裸连排，竖图叠成高塔太占空间。定为：全部截图包在一个 `<p align="center">` 里连续写，img 之间无空行（隔空行 GitHub 渲染成独立段落，正是高塔成因），宽度统一百分比（`32%`，宽屏一行三张、窄屏自动降级；定长 px 在窄屏会回退成竖排）。参照 Material Files 的 32% 百分比写法。NewPipe 是 160 px 固定值，机制相似但窄屏表现差，不取。Obtainium 的表格网格同被否。存量改造时先备图再动结构。
- **图标放标题正上方居中**（2026-10-13 定）。本机多个项目 README 一张图没有，有正式图标的项目应展示。宽度 96 到 144 px，命令行工具与库可省略。
- **快速开始只写实际用的那一套命令**（2026-10-13 提炼）。脚手架模板把 npm/pnpm/yarn/bun 四套等价命令都列上、环境变量只写占位符不写出处，是本机多个 README 实际存在的两类问题。
- **README 不写会过时的动态**（2026-10-13 提炼）。版本号、当前主线、最近发布状态链到 Releases 或项目文档，不写在 README 正文。与发布说明规范的禁用节同源。
- **引用实测写通用说法**（沿用本机约定）。具体仓库名与本机路径不进公开文档，反面实证写「某个只有两条命令的 README」这类通用描述。

### 打包与用法

- **装法选 git 源，不用本地路径源**（2026-09-29 定）。需求是「上游有新提交时，启动 Pi 能自己提示」，而本地路径源在更新检查里被直接跳过（`parseSource` 得到 `type === "local"` 就 `return undefined`），永远不会提示。git 源每次启动 Pi 都会异步比对本地 HEAD 与远端，落后就弹一条带 `pi update --extensions` 的提示。
- **git 源走 HTTPS，不经 SSH**（2026-09-29 核实）。`parseGitUrl` 会把 `git:github.com/<owner>/<repo>` 转成 `https://github.com/<owner>/<repo>` 再克隆，所以本机 SSH 22 端口不通不影响安装与更新。
- **三种装法的更新行为不同**（2026-09-29 核实）。git 源有提示、能 `pi update --extensions`；手动复制到 `~/.pi/agent/skills/` 什么都不提示；本地路径源提示也不做，但改文件即生效。维护仓库时临时用本地路径源可以，但会失去更新提示，两者不可兼得。
- **同名技能冲突时先被发现的那份生效**（2026-09-29 实测）。同时装 git 源与手动副本，`skills/` 目录排在 git 目录前面，结果加载到的是旧副本，而只有一条 collision 诊断。换装法时先把旧的一份删干净。
- **不做 marketplace 结构**。技能目录平铺在仓库根，不塞进 `skills/` 之类的层级。用法是「给仓库地址，自己装」。
- **技能分两级加载**（2026-09-29 核实）。名称与描述在会话启动时写进系统提示，正文（`SKILL.md`）在任务匹配时才读取。所以改文本内容后，新会话直接生效；运行中的会话只需 `/reload`。Pi 没有文件监听，不会有改完自动生效的错觉，但也不需要重启进程。
- **README 的用法一节以 Pi 为例**（2026-09-25 定）。先给 `pi install` 这一条，再给复制目录的两种落点，全局与项目级各一，另有临时加载的写法。其他工具只留一句「换成对应的技能目录」。
- **README 里单独指代执行者时写 `Agent`**，首字母大写。`Agent Skills` 是规范名，本来就是大写。
- **支持 `pi install`，靠根目录的 `package.json`**（2026-09-25 加）。包清单是 `pi.skills` 数组，逐个列技能目录。**没有清单时只从包根的 `skills/` 子目录发现技能**，本仓是平铺的 `<技能名>/SKILL.md`，所以清单是必需的。不想为了打包挪目录，就写了清单。包里只有 `package.json`，没有 `dependencies` 与 `peerDependencies`，所以安装那步不碰网络，也不触发 peer 依赖问题。加技能或改目录名时两处要一起改。
- **验证打包行为优先直接调包内导出，别跑真模型**。包管理器能给出完整的资源解析结果，技能加载函数能验技能目录。传一个临时配置目录进去就完全隔离，不碰真实的全局配置。

## 四、容易踩的坑

- **新建仓库先核对有效提交身份**。2026-09-25 建仓库时，错误的默认身份曾导致账号归属问题。现有提交身份由机器级约定维护，接手时注意仓库覆盖配置；不把历史改写当作默认修复。
- **行尾用 `.gitattributes` 固定成 LF**（`* text=auto eol=lf`），否则检出设置会把 Python 脚本变成 CRLF。
- **扫描脚本的降噪判据要覆盖引号与 frontmatter 里的内容**。见「定下来的决策」里的扫描脚本一条。
- **本地路径源与手动副本不能同时存在**。两者技能同名时 Pi 只报一条 collision 诊断，然后让先被发现的那份生效，结果就是仓库里改了但会话用着旧副本。换装法前先删干净旧的一份。
- **`timeout` 是 Windows 版**。`timeout 60 <命令>` 会报「无效语法，默认选项不允许超过 '1' 次」，而且不会执行任何东西。

## 十三、2026-10-16：排查 GLM 压缩报错，确认与配置无关

- 现象：使用 `opencode-zen-free/glm-5.3-flash-free` 时压缩报 `429 rate_limit_error`，`OpenCode Zen Free: Upstream request failed: Endpoint is unavailable.`
- 排查手段：直接向本机 magpie 网关（`127.0.0.1:3425`）发对照请求，不依赖 Pi 会话。关键对照是**把请求缩小到 16 token**，同样报同一个错，因此与压缩、与请求体量、与会话亲和头都无关。
- 结论：故障在 GLM 免费端点侧，按时间聚簇出现。实测同一天内先 2/2 失败，再 6/10 成功，最后 15/15 成功；同规模 `deepseek-v4.1-flash-free` 请求正常。故障窗口内端点极慢：340 token 请求 67 秒，13k token 请求 224 秒，另有超时；失败是快速拒绝（约 10 秒返回 429），不是超时。
- 为什么压缩最先出问题：压缩是一次投出整段会话（触发点 180k），并且要求很长的输出（摘要 `maxTokens` 是 `0.8 × reserveTokens`，即 16000）；失败后 Pi 那次恢复只覆盖上下文溢出与提前 length 结束，不管 429，所以用户直接看到报错。
- 顺带查实：压缩只能用当前会话模型。`compaction.modelOverrides` 只接受 `reserveTokens` 与 `keepRecentTokens` 两个 token 字段，没有换模型的写法，做不到聊天与压缩用不同模型。
- 验证边界：未改变任何配置，未验证 Pi 层压缩重试次数。免费端点的稳定性属服务侧状态，不写成机器约定，只用测量值记录。
- 下一步：免费端点出故障窗口时手工 `/compact` 重试，或改用更健康的模型；不再作为配置问题重复排查。

- 同一个项目还发现资产名与仓库改名不同步：`chuxing-<版本>.apk` 应为 `SevenTrip-<版本>.apk`，`Action-Launcher-Enhanced-<版本>.apk` 应为仓库名 `ActionLauncherEnhanced-<版本>.apk`（提交 `7dcea09`、`5319a2e`、`fc53e73`、`0601b57`）。
- 线上整改：29 个 Release 的资产改名 47 个、`.apk.sha256` 同伴改名 10 个、`SHA256SUMS*` 内容改写 15 个、正文引用 39 处，另外清掉 6 个资产的标签。做法与验证方式写在规范收录的历史回填流程里：先备份正文与资产清单，再逐个 Release 比对资产数量与产物字节数，最后抽包实测 SHA-256。
- 教训：**`gh release create` 里的 `#` 后缀会在页面上替代文件名显示**，而这一点此前只记成「多一行标签」。整改历史 Release 时容易只盯资产名，漏掉 `label`；用 `gh api` 查资产时要一并看这个字段。
- 命名取当时还是现在的名字：项目改名前的历史 Release 用当时的产品名（如 `MiPush-general-<日期>.apk`），改名后的用当前名，避免给旧版本套上后来才有的名字。
