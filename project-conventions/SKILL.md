# 项目开发规范与交接

在一个项目里干活，先把七件事立好规矩：

- 凭据不出会话，私钥只让工具直接使用。
- 项目约定只有一处，写在项目的 `AGENTS.md` 里。
- 进度有记录，写在仓库里，下一个执行者用任何工具都能接上。
- 每件事开工前有预期时长，超了就停下来报告。
- 测试产生的临时产物用完就清，不在设备与仓库里留垃圾。
- 开发中间产物集中放在项目内一个被忽略的容器里，用完就回收。
- 工具和环境装一次全项目共用，会改变产物的工具按项目固定版本。

## 凭据与私钥

### 私钥只能被直接使用

允许的做法：让 SSH 客户端、Git、`scp`、`rsync -e ssh`、`ssh-agent` 拿着私钥去连接和传输。密钥材料全程留在文件里，由工具自己读。

不允许的做法：读取、解密、复制、打印、比对、备份私钥内容。`cat`、`head`、`xxd`、`strings`、`openssl rsa`、`ssh-keygen -y` 读私钥都在禁止之列，哪怕只是想确认格式。这类命令一旦执行，密钥材料就进入了会话记录，等同泄露。

确认私钥能不能用，用连接本身验证，不要去看密钥：

```bash
ssh -o BatchMode=yes -o ConnectTimeout=5 <host> true
```

确认连接走的是哪把钥匙、哪个代理，只看配置与远端：

```bash
grep -nE '^(Host|HostName|IdentityFile|ProxyJump|ProxyCommand)' ~/.ssh/config
git remote -v
```

私钥口令由用户本人输入。不代填、不写进脚本、不放进环境变量文件，也不让 `ssh` 之外的工具接触它。

### GitHub 与远端访问走 SSH

连 GitHub 的仓库操作（`git clone`、`fetch`、`pull`、`push`、推标签）一律用 `git` 加 SSH 远端 `git@github.com:<owner>/<repo>.git`。要访问 GitHub 不等于要 token：私钥已经在 `~/.ssh` 里，让它生效就行，不要回头问用户要凭据，也不要重新生成密钥或改用 HTTPS。

私钥放在 `~/.ssh` 下的默认文件名（`id_rsa`、`id_ed25519`）。要区分多个身份时在 `~/.ssh/config` 里用 `IdentityFile` 指定；不把密钥挪到项目目录，不放 `.env`，不写进脚本。

`gh` 留给只有 API 才能做的事：读写 Release 与资产、Actions 运行与日志、Secrets、PR 与 Issue、跨仓库查询。它通常已是登录状态（系统 keyring），不必再让用户登录一次。

接手已有仓库先看远端用的是哪种协议，不是 SSH 就改一次：

```bash
# 期望输出 git@github.com:<owner>/<repo>.git
git remote get-url origin
git remote set-url origin git@github.com:<owner>/<repo>.git
# 返回 Hi <账号>! You've successfully authenticated 即通；该命令退出码为 1，属正常
ssh -o BatchMode=yes -o ConnectTimeout=5 -T git@github.com
```

这个检查只发连接，不碰密钥。上一节的读取禁令照旧：私钥只让 `ssh` 与 `git` 自己读。

### 其他凭据同理

API token、证书私钥、keystore 口令、数据库密码、云厂商密钥都属于同一类东西。要引用它们时走既有通道：环境变量、`.env`、`git credential.helper`、`gh auth`、系统 keyring。命令里不出现明文，日志里不出现明文。

### 读文件前先确认

读服务器或仓库里的配置文件之前，先看文件名、大小和目录，判断它是否可能装凭据。确认过再读全文。

有一条真实教训值得记住：为了确认 TLS 复用形态，直接 `cat` 了含 DNS API token 的配置，token 进入会话记录，最后只能轮换。代价和收益完全不成比例，而那次想确认的信息，`grep` 一两行就能拿到。

### 已经泄露时

- 立即告知用户，说明读了什么文件、为什么会读到、后果是什么，并建议轮换。
- 不在回复里复述凭据明文，也不把明文写进任何文档或提交。
- 记录事故时写清机制和影响，不抄凭据本身。

### 提交前自查

```bash
git diff --cached | grep -nE 'BEGIN [A-Z ]*PRIVATE KEY|ghp_|github_pat_|xox[baprs]-|AKIA[0-9A-Z]{16}'
```

命中就停下来处理，不要先提交再想办法。

## 接手项目先查已有记录

新会话接手一个项目、或开一个新项目之前，先花一两条命令确认有没有历史记录。少了这一步，会把已经定过的约定重新推断一遍，用户还得从头交代。

跨项目档案放在一份私有仓库里，本机路径记在本机 Pi 的通用指引中。查的顺序固定：

1. **项目索引**：按 GitHub 仓库名定位，保留大小写。本地目录名可能与仓库名不同，别拿目录名当身份。
2. **该项目的私有约定**：`projects/<仓库名>/AGENTS.md`，记着这台机器上该项目的路径、凭据位置、设备语义与历史踩坑。
3. **本机与工作区基线**：记的是跨项目成立的配置与工具现状。
4. **仓库内的进度与决策**：`docs/handoff/` 的最新条目、长期决策文件，以及 `docs/STATUS.md` 这类常驻头。

```bash
grep -n "<仓库名>" <档案仓库>/PROJECTS.md    # 定位映射
ls <档案仓库>/projects/<仓库名>/             # 有没有私有约定
ls <项目目录>/docs/handoff/ 2>/dev/null      # 有没有进度记录
```

查到记录之后：

- **已有记录算权威**。与现场不一致时以仓库内明文和实际配置为准，并把差异报告出来，不默默照旧记录做。
- **本轮确认的事实补回对应层**：项目专属的进该项目归档，跨项目成立的进机器级或工作区级，项目进度进仓库的 `docs/handoff/`。三层别混写。
- **没有记录时**按模板建档并在索引里登记，不建空目录，也不放占位文件。

接手阶段先把「读到了什么、哪条与现场不符」报告清楚再动手。用户没指定任务时，报完上下文让用户挑项目。

## 项目约定文件（AGENTS.md）

### 分层

约定按作用范围分三层，项目级只写项目特有的东西：

- **机器级**：这台机器的工具、路径、代理、JDK、SDK 等，所有项目共用。
- **开发根目录级**：某一批项目的共同要求，例如回答语言、图片读取授权。
- **项目级**：只对当前仓库成立的事实与规则。

上层已有的内容不要在项目级重复一遍。重复之后，两边改动不同步，读者也不知道该信哪一份。

### 项目级该写什么

- 回答语言与风格要求。
- 必须遵守的流程：分支策略、验收方式、合入与清理、发布顺序。
- 构建、测试、发布的命令与关键路径，以及不能违反的工具约束。
- 环境与工具的实际位置和版本约束。
- 写入边界：哪些目录可以自由写，哪些操作必须先取得授权。
- 凭据与外部访问：凭据放在哪、用哪个通道引用，只写位置不写内容。
- 术语表与命名约定，包括哪些词在本项目里是正式名称。
- 可复现的已知坑，写清现象、原因和绕法。
- 决策记录：谁在什么时候定下什么，替代了哪条旧约定。

### 项目级不该写什么

- 密钥、令牌、口令，任何形式都不写。
- 进度流水、每日动态、本轮结论，这些属于进度文档。
- 一次性命令、临时故障、未经验证的推测。
- 上层已经写过的通用规则。
- 从别处抄来的、和本项目无关的规范。

### 约定文件也要守预算

约定的作用是「每轮都在场」，所以每一行都要付每轮的成本。项目 `AGENTS.md` 控制在 100 行以内，超了说明低频内容混进来了。两类去路：

- 值得入库的（构建排错细节、专项操作手册），移到 `docs/` 专项文档，约定里留一行指向。
- 值不得入库的（一次性的经验、只和某台设备有关的细节），留在不入库的小抄里或就地删除。

机器级与工作区级约定同样收敛：旧环境快照压成几行摘要，失效条目就地删，不靠「留个历史」来交代。

尾部设一节「文档索引」，一行一个：进度文档、专项文档、构建手册各指向哪。接手的人按索引跳转，不靠全文记忆。

### 维护方式

- 写之前先验证事实，别把推测写进去。
- 新决定要显式写明替代了哪条旧约定，避免两套说法并存。
- 旧条目失效时就地修订，不保留新旧两份说明。
- 每轮任务确认了新的稳定事实后就更新，不攒到最后一次写。

### 本地文件边界

项目的 `AGENTS.md` 通常只服务本地开发，不加入 Git、不推送、不进发布产物。接管仓库时用仓库本地的 `.git/info/exclude` 忽略它。发现它已被跟踪，就保留本地文件并从仓库中移除索引。

需要团队共享的工程约束另写公开文档，不能让本地约定文件成为唯一来源。

## 开发进度文档（交接记忆）

### 作用是交接，不是日记

进度文档存在的唯一理由，是让下一个执行者不用重读整个仓库和整段会话，就能接着干。写的时候只想一件事：对方看完能不能直接动手。

### 放仓库里，不放助手私有目录

进度文档是项目资产，不是某个助手的工作笔记。

- 写在仓库目录下，跟代码一起提交，**进 Git**。
- **不放进任何助手或工具的私有目录**：`.pi/`、`.claude/`、`.workbuddy/`、`.cursor/` 这类一律不用。它们要么被忽略、要么换了工具就没人看，做不到交接。
- 不为某个软件做特化。谁克隆仓库都能直接读到，不需要先装某个助手，也不需要在它启动时才加载。
- 私有目录只允许放临时草稿：调试日志、一次性脚本、截图。草稿不是交接依据，别把它当进度记录用。

这一条与项目 `AGENTS.md` 的可见性正好相反，很容易搞混：

| | 项目 `AGENTS.md` | 开发进度文档 |
| --- | --- | --- |
| 是否入库 | 不入库，用 `.git/info/exclude` 忽略 | **入库，跟代码一起提交** |
| 装什么 | 机器路径、凭据位置、设备信息、本地授权范围 | 干了什么、验证到什么程度、下一步 |
| 读者 | 本机上的助手 | 任何人、任何工具 |

因为进度文档是公开的，它不能写内网地址、服务器路径、设备序列号、凭据位置或口令。需要指向这些信息时只写一句「见本地 `AGENTS.md`」，把具体值留在那个不入库的文件里。

### 选形态与体量预算

两种形态都可以，选一种固定下来，**两种都放在仓库目录下**，头部必须有「当前主线」小节：

- **单一时间线**：`docs/STATUS.md`，一条一条追加，适合长期项目。条目多了以后按编号或日期检索。
- **决策文件加日期流水**：`docs/handoff/DECISIONS.md` 记长期决策（只在被推翻时才改），`docs/handoff/YYYY-MM-DD.md` 记当日流水。适合一天内多轮交付的项目。

无论哪种，都要有一个能被 `grep` 命中的固定开头，例如日期加序号。

文档是给执行者读的，读了就要花时间与 token。按读法分两层，预算写死：

- **常驻头**：进度文件头部的「当前主线」，两三句加接手入口，二十行以内。接手的人读完头就能动手，不必翻条目。
- **条目池**：头之下的全部条目。只按需读单条，不默认整读。

| 对象 | 预算 | 超限动作 |
| --- | --- | --- |
| `STATUS.md` | 不超过 500 行或 30 条 | 已完结条目整批归档，见「归档与形态升级」 |
| 单条记录 | 不超过 30 行 | 超了说明把过程流水写进来了，砍到结论、验证与边界 |
| 项目 `AGENTS.md` | 不超过 100 行 | 低频内容析出，见「约定文件也要守预算」 |

预算判据是行数。文件大到需要滚动才能看全的时候，读它的成本已经超过它的价值。

### 归档与形态升级

历史记录的价值在「需要时能查到」，不在「一直摊在桌面上」。

- **归档**：超过体量预算时，把已完结的旧条目整批移到 `docs/archive/STATUS-<起始日期>_<截止日期>.md`，一次成型之后保持只读，往归档里追加即违规。正文头部留「当前主线」、最近几条与归档索引（写明各归档文件覆盖哪段日期），需要旧事实的人照索引定位，成本从「整读 500 行」降到「grep 单条」。归档前先提交一次现状，切分动作可整体回滚。
- **形态升级**：单一时间线的条目里，「确立或推翻长期决策」类内容积到三条以上，迁到决策加日期流水形态：把决策析出进 `DECISIONS.md`，进度文件继续按日期走。迁移时旧 STATUS 改名或归档，不在里面继续混装。

### 读取协议

文档写多大是一半，另一半是读多省。写进约定里的默认读法：

- **接手**：读 `AGENTS.md` → 文档索引 → 进度头部「当前主线」→ 需要细节才读最新一条。默认不读全量历史；确要历史，按日期定位单文件。
- **找具体事实**：先看文件规模（`wc -l`），超过预算的文件禁止整读，用 `grep` 命中条目固定开头后按行号取那一节。
- **写入**：只追加或修订条目，不为「整理」重写全文件。整读加大文件再整写一遍，token 成本是单条写入的两倍以上。
- **更新头部**：每轮收尾顺手把「当前主线」改成现状，让下一个接手的人真的能只读头部。

### 一条记录写什么

- 日期与本轮目标。
- 改动的仓库、分支与提交 SHA，部署则写清镜像或版本号。
- 验证方式和结果：跑了什么命令、观察到什么现象、多少条样本。
- 结论与其边界：哪些是实测，哪些是推断，哪些没覆盖。
- 未完成项与下一步。
- 被推翻的旧结论要指名作废，并给出反证依据。

### 不写什么

- 对话寒暄、过程性试错的长日志、被放弃方案的完整细节。
- 没有核实的推测当成结论写。
- 能通过 `git log` 查到的东西原样抄一遍，只留 SHA 与一句话说明。
- 内网地址、服务器路径、设备序列号、凭据位置与口令。入库的文档一律不写，用本地方便文件承载。

### 更新与提交时机

任务收尾、分支合入、部署完成、实验得出否证结论、发现旧记录有误时，都当场更新。

进度文档跟当轮代码一起提交，不单独开分支攒着。它的价值在于和提交对应，攒着写会丢掉当时的上下文。

### 交接时怎么读

1. 读 `AGENTS.md` 与它尾部的文档索引，按索引定位进度文档。
2. 读进度头部的「当前主线」，建立大局。
3. 需要近期细节时读最新一条；需要历史时按日期或序号定位，不整读全文件。
4. 现场核对状态，不凭记录相信：`git status`、当前分支、`git log -1`、CI 结果。
5. 找未完成项和阻塞，确认它们是否仍然成立。
6. 确认凭据、设备、外部服务的可用状态，再开始动手。
7. 发现记录与实际不符时，先查清哪边是新的，再修订记录。

进度文件超过体量预算时先 `wc -l` 看规模，超过 500 行禁止整读，`grep` 定位单条后按行号取。记录里的 SHA 和状态是当时的快照，读的时候要核对当前值，不能直接沿用。

## 任务预期与超时

### 先给出预期，再动手

跑任何可能超过十几秒的命令前，先说清三件事：这步要做什么、大概多久、超时就怎么办。没有预期就没有「卡住」这个判断，只能一直等下去。

```text
预期：全量测试约 3 分钟，给 6 分钟超时；超过就改跑单模块并报告。
```

### 命令必须带超时

- 秒级命令直接跑。
- 分钟级命令显式设超时，不留无限等待。用工具的超时参数，或让命令自己带限制：

```bash
timeout 600 ./gradlew test
curl -sS --max-time 30 -o out.bin "$url"
```

- 安装依赖、下载、网络请求、连远程设备这几类必须设超时。它们卡住时通常不会自己报错。
- 不要用后台进程加轮询来绕开超时。那样等待时间只是换了个地方，问题没解决。

### 超时后的动作

第一次超时的正确反应是缩小范围，不是原样重跑：

1. 确认进程真的结束了，别留下孤儿进程占着端口或锁。
2. 先跑最小可用单元：单条用例、单个模块、单次请求。能过说明是规模问题，不能过说明是环境或代码问题。
3. 把输出写进文件再分段读：`./gradlew test > /tmp/test.log 2>&1`，然后只看尾部与失败行。超长输出直接回传会淹没会话。
4. 第二次仍然超时，就停下来报告，不试第三次。

### 停下来的报告格式

```text
卡在哪：<命令与当前状态>
已确认：<这一步排除掉什么>
需要：<用户要做的决定或提供的条件>
建议：<下一步的最小验证>
```

一句话说「还在跑」不算进展，也不算汇报。

### 长任务分批推进

- 分批执行，每批报一次进度：扫 200 个文件分四批，每批 50 个。
- 大范围扫描、批量改文、大仓库克隆这类工作，先估算规模再决定批次。
- 批量操作先做一份全量校验，再落盘，不要一边跑一边改。

### 什么时候必须停下来问

- 任务规模明显超出预期，例如「先扫一下」实际是十几个 GB。
- 需要跨越授权边界，例如写项目目录外的位置、改动服务器。
- 同一件事连续两次失败，原因还不明确。
- 用户取消过一次的操作，不要在没说明原因的情况下重试同一形态。

## 真机是用户的设备

测试用的手机是用户日常在用的设备，里面有真实数据和使用习惯。开发时的操作按侵入程度分三档，越界的先问。

**必须先问**：

- **重启、关机、恢复出厂**。`adb reboot` 只是一条命令，代价是打断用户手上的一切，并且让后续调试状态不可复现。
- **卸载应用、清除应用数据**：`adb uninstall`、`pm uninstall`、`pm clear`、`pm disable`。
- **改系统状态**：`adb root`、`adb remount`、`settings put`、禁用或移除系统应用、切换默认应用（启动器尤其明显，会直接换掉用户的主屏）。
- **刷机、改分区、改系统属性、动 Magisk 与 LSPosed 这类框架**。

问的时候说清为什么必须做、影响是什么、有没有替代（比如先在模拟器上验证）。授权只对当次有效：用户在这个任务里同意过一次重启，不代表下一个任务可以自己重启，「上次同意过卸载」也不是长期许可。

**覆盖安装失败时不要自己卸载重装**：

签名不符、`versionCode` 没递增、ABI 不匹配都会让 `adb install -r` 失败。这时 `adb uninstall` 再全新安装是最坏的处理：应用数据、登录状态、用户攒下的配置一起没了，而这些往往正是要保留的东西。

停下来说清三件事：

1. 完整错误码与原因，例如 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`、`INSTALL_FAILED_VERSION_DOWNGRADE`、`INSTALL_PARSE_FAILED_NO_CERTIFICATES`。
2. 可选路径与各自的代价：换上与设备现有签名一致的包、递增 `versionCode`、换空闲设备或模拟器。
3. 让用户选。确实要在真机上卸载重装时，由用户自己动手，或明确同意后再做。

**可以直接做**（前提是用户已同意在这台设备上装这个应用）：

- 覆盖安装同签名的包：`adb install -r`。
- 启动、停止、看日志：`am start`、`force-stop` 目标应用、`logcat`、截图、`dumpsys`。
- 从设备拉文件到容器目录（落点规则见「从设备取材」）。
- 有风险的动作先在模拟器上验证：切默认启动器、重启、改权限与系统属性都能在模拟器上跑通，确认无误再跟用户约真机时间。

这节有实际出处：一个启动器项目上，助手为了验证一遍重启了真机。另一次 `adb install -r` 因签名不符失败，助手自己 `adb uninstall` 再全新安装，把用户攒的配置清掉了。

## 测试临时产物的清理

### 用完就清，不留在设备上

自动测试、调试、验证过程中，为了看内容而生成的东西都属于临时产物。看完了就删，不要留在设备、仓库或远端机器上。

常见的有：

- 设备上的截图、UI dump、日志、导出文件（`/sdcard`、`/tmp`、下载目录）。
- 推送到设备或远程机器的安装包、脚本、夹具。
- 仓库与工作目录里的临时脚本、扫描输出、验证夹具、编译中间产物。
- 为排查而临时加的日志文件、转储、导出。

### 收尾前确认本轮临时文件已清

把清理当成验收的一部分，不是可选项。任务收尾、交接前、离开机器前，确认本轮自己生成的文件都已处理掉。

- 记下本轮生成了什么，而不是靠回忆。开动前先在心里列一份清单，收尾时逐项核对。
- 清理范围**限于本轮明确生成的文件**。不得用宽泛通配符删目录、删缓存、删来源不明或属于用户的数据。区分不了来源时，先问，不要先删。
- 清不掉的东西（需要保持运行的服务日志、别人正在用的数据）要明确说出来，不能默默留下。

### 长期产物与临时产物分开

需要留下的测试产物（基线截图、黄金样本、必须入库的夹具）当成项目资产处理：放进仓库的固定位置并提交，在进度文档里说明用途与生成方式。它与临时产物的区别只有一条：**有人会再次用到它**。

不确定会不会再用到时，先按临时处理并删掉；确实需要再生成一次的成本通常很低，而设备上堆垃圾的成本会一直累积。

## 开发中间产物的留存与回收

测试产物用完就清。开发中间产物不一样：在一条主线上它要跨多轮存在，但绝不能越堆越多。整件事只有一个判据。

### 判据：能不能用仓库里的东西重新生成

- **能重新生成** → 缓存。解包树、反编译产物、生成树、构建缓存、模拟器与系统镜像、下载的工具链都是这一类。缓存随时可以整目录删掉，删完重跑脚本即可。
- **不能重新生成** → 资产。源码、补丁、生成脚本、基线样本、需要入库的夹具放进仓库固定位置并提交，在进度文档里说明用途与生成方式。
- **从外部取回的素材**（设备拉的文件、日志、dump、导出）另算一类：既不是资产也不是缓存，是本轮原料，用完就清，不跨主线。

判据拿不准时按缓存处理，删前实际跑一次生成命令确认能重生，不凭印象。本轮生成的一次性产物仍按「测试临时产物的清理」办，这一节管的是要跨轮存在的容器内容。

### 容器：一个项目一个，必须被忽略

- 中间产物集中放在项目内**一个**容器目录里，命名沿用项目既有约定（本机拼音项目是 `work/`），必须在 `.gitignore` 中，容器本身不入库。
- 容器内按用途分子目录（解包、构建、设备取材各一个），不按日期无限新建。
- 散落在仓库根、源码目录旁、用户主目录根或开发根目录的中间产物都算违规，发现即移进容器或删掉。
- 同一种原料只留一份。第二次解包、第二次反编译之前先看容器里有没有现成的，要重来就先删旧的，不要并存两棵树。

### 回收时机

前三条比体积上限更重要：

1. **任务收尾、验收通过**时删本轮产物。
2. **换主线、切分支、换版本目标**时删上一轮的缓存目录。需要就重跑脚本，不留树。
3. **同一种原料要重做**时先删旧的再生成。
4. **超过体积上限**时，从最旧最大的缓存开始删。

体积上限是兜底，不是回收计划。本机默认：单个项目的容器不超过 10 GB，`E:\Dev` 下所有容器合计不超过 30 GB。到了这个量级说明回收时机一直没执行。

### 从设备取材

- `adb pull` 的目的地必须是容器内的固定子目录（例如 `work/device/`），不允许落在仓库根或开发根目录。一个任务一个目录，收尾删整个目录。
- 往设备写临时文件时用自己的目录（例如 `/sdcard/Download/<项目前缀>/`），不塞进公共目录根，用完精确删除。
- 设备侧清理仍按「测试临时产物的清理」，两边在同一轮收尾里一起做。

### 顺手查一下

```bash
# 各项目的容器体积（容器名按项目约定，拼音项目是 work/），超上限的处理掉
du -sm */work 2>/dev/null | sort -rn

# 有没有被忽略的产物散落在容器外
git status --ignored --short
```

## 工具与环境的共用基线

配环境的时间只花一次。判断哪些共用、哪些按项目固定，界线只有一条：**版本会不会改变构建输出**。

### 共用：环境与查看类工具

JDK、Android SDK、各语言运行时、Gradle 发行版与依赖缓存、模拟器与系统镜像、adb、反编译与查看工具、压缩与媒体工具，装一次全项目可用，任何项目不再复制一份。

装之前先查，不凭印象重装：

- 命令行工具看包管理器的已装列表（Windows 上是 `scoop list` 或 `~/scoop/apps`）。
- 脚本要用的 jar 先看项目文档有没有记位置。
- 已装且够用就直接复用，需要新版本就地升级，不并存两份。

各语言的依赖缓存天然共用，不为单个项目设私有缓存目录，除非项目明确写了理由。

### 按项目固定：会改变产物的工具

apktool、签名工具、Gradle Wrapper、各构建插件按项目固定版本，不做全局共用。共用一份等于让所有项目跟着动，解码语义和产物字节都会变，历史验收结论随之失效。这类工具的版本与获取方式写在项目文档里，不写在共用位置。

### 环境变量以用户级配置为准

长活会话继承的是启动时的环境，注册表改过之后进程里还是旧值。核对环境读用户级配置，不相信当前进程看到的变量：

```powershell
[Environment]::GetEnvironmentVariable('JAVA_HOME','User')
```

新开的终端才会拿到新值。已记录的路径要实际解析一次确认存在，指向不存在的目录是最常见的失效形态，也最容易被当成「工具没装」而重装一遍。

### 旧版本与安装包要回收

工具自身也走回收，多余版本和安装包缓存定期清掉（Scoop 上是 `scoop cleanup *` 与 `scoop cache rm *`）。留一份当前版本就够，旧版本没有任何回滚价值。

## 交接清单

给下一个执行者的最小信息集，可以直接复制去填：

```markdown
## 当前状态

- 仓库与分支：<仓库> / <分支>
- 提交：<SHA>，工作区<干净 / 有改动>
- CI 与部署：<结果与版本>
- 设备与环境：<设备、代理、外部服务是否可用>

## 本轮完成

- <改了什么，验证到什么程度>

## 未完成与阻塞

- <事项>：<卡在哪，需要什么才能继续>

## 下一步建议

1. <动作> → <验收方式>
```

## 接手新项目时的适配清单

- 跨项目档案里有没有这个项目的记录，读过没有，哪条与现场不符。
- 约定文件在哪，是否已从 Git 索引移除，有没有尾部文档索引，行数超不超预算。
- 进度文档在哪，用哪种形态，头部有没有「当前主线」，超不超预算，有没有归档目录。
- 凭据放在哪，用哪个通道引用。
- 构建、测试、发布的命令，以及版本号的唯一来源。
- 外部访问的授权范围，哪些操作必须再确认。
- 回答语言与文案规范，引号风格尤其要先看一眼。
- 哪些命令是分钟级甚至小时级的，各自的可接受时长是多少。
