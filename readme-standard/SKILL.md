# README 撰写标准

README 是仓库的门面。读者是第一次见到这个仓库的人，包括半年后回头看的自己。

这里管结构、边界与完整性：节怎么排、什么内容进门面、什么内容留在外面的文档里。句子、段落、排版与标点仍按 [chinese-tech-writing](../chinese-tech-writing/SKILL.md) 执行，两个技能不互斥：本技能定框架，遣词造句落到句子层面时换它接手。

骨架模板在 [references/skeleton.md](references/skeleton.md)，写新 README 时复制那份开始改。

## 节顺序

固定骨架是下面这列。节可以省略，不乱序。只有项目确实有对应内容时才加节，不为凑齐补空节。

1. 图标与标题
2. 定位语
3. 截图（有可视界面就放）
4. 特性（可选）
5. 快速开始
6. 使用与配置（内容多就拆成几节）
7. 设计与实现（可选：技术选型、目录结构、构建方式）
8. 文档
9. 许可证

前三样决定读者走不走下去，中间是上手路径，最后留出处。判断一节去留的标准：删掉它，读者会不会在某一步卡住。不会就删。

## 图标与标题

应用图标放标题正上方居中。多数项目的 README 一张图没有，读者连这是什么应用的界面都想象不出来。有正式图标的项目没有理由不放。

推荐写法，标题与图标都居中：

```html
<div align="center">
  <img src="docs/images/icon.png" width="120" alt="项目图标">

  # 项目名
</div>
```

图标居中一列的细节：

- 路径放仓库内固定位置，`docs/images/icon.png` 是默认选择。已有 Fastlane 元数据的 Android 项目可以直接引用 `fastlane/metadata/` 里的图标，不复制第二份。
- 宽度 96 到 144 px，太大就喧宾夺主。
- 图标是可选的，命令行工具与库可以换成文字 logo 或干脆没有，但有的项目必须放。

## 定位语

标题下面，不设小节标题，两三句：这是什么、解决什么问题、一句现状。读者读完这两三句 decides 要不要继续往下看。

写法的三条边界：

- 讲问题与能力，不讲技术路线。技术路线放「设计与实现」。
- 不写会过时的动态。版本号、当前主线、最近发布状态这些内容一写就会过期，链到 Releases 或 `docs/` 让它自己更新。
- 有不能公开的东西、或法律边界需要先声明，用引用块接在定位语后面，一段说完。

仓库语言用中文。面向国际读者的项目用英文，但全文一种语言，不中英交替。

## 截图

紧跟定位语。读者第一件事是看界面长什么样、操作起来像不像自己要找的东西，所以截图往前放，不藏在文末。

一节 `## 截图`，图片直接排列，不放进表格：

```markdown
<img src="docs/images/main.png" width="270" alt="主窗口">
<img src="docs/images/settings.png" width="270" alt="设置页">
<img src="docs/images/keyboard.png" width="270" alt="键盘">
```

连续写、不空行分隔，页面会自动横向铺开，占满就换行，不需要表格模拟网格。

规则：

- **同一组截图同一个 width。** 宽度不一排出来大小不齐，看着就乱。手机竖屏截图在 240 到 300 px 里取一个值，270 是常用量级。Markdown 的 `![alt](路径)` 语法控制不了宽度，要定宽就写 `<img>` 标签。
- 不用表格排列，HTML 表格与 Markdown 表格都不用。表格把截图钉死成固定网格，还容易退化成逐图解释。这条是用户看过线上效果图后否掉的：两栏表格也算表格，不要。有个现有项目曾用 HTML 表格逐图配说明，读起来像产品宣传页，连表格带说明一起已被否掉。
- 截图数量一到四张，挑最能说明应用用途的，凑数的不放。
- 不要逐图配说明文字。图里是什么，读者看得到。确实需要一句语境（比如「深浅色两套主题」），写在这一节开头，一句话，概括整组图。
- 截图放 `docs/images/`，文件名写内容不用序号：`material3-settings.png` 这种，不叫 `1.png`。
- 截图里如果有敏感信息（IP、邮箱、序列号、真实用户数据），先遮挡或换演示数据再提交。截图是要公开的门面。
- 图标、截图、正图的图片文件都放这里，README 引用相对路径。外链图床不进仓库，仓库一移图就死。

没有界面的项目没有这节，跳过。

## 快速开始

从 clone 到跑起来的最短路径。这一节是 README 里最容易凌乱的地方，因为脚手架生成的模板把每种包管理器的命令都罗列一遍。规则：

- **只写实际用的那一套命令。** 项目用 pnpm 就写 pnpm，不把 npm、yarn、bun 的四套等价命令都列上。读者想知道的是这个项目怎么跑，不是包管理器对照表。多套共存的项目写主用的一套，其余放「也可以」一句。
- **每条命令要能直接复制执行。** 命令前一行说明它是干什么的，或命令后接一句。裸命令块没有上下文，读者不知道跑完会发生什么。
- **环境变量写出处。** `NPSSO=your_npsso yarn run test` 这种命令，`NPSSO` 是什么、值从哪拿、格式是什么，必须有一句交代。只写占位符不写获取方式，等于把读者拦在门外。
- **前置条件在命令之前。** 需要的运行时与版本、需要先启动的服务、需要手动开着的调试开关，先列出来再给命令。
- 安装方式多于一种（例如同时支持源码运行和下载安装包）时，分开小节，各给最短路径。

## 使用与配置

核心功能的用法。小项目写几条常用操作就够，大项目这里只放最常用的一两个场景，其余链到 `docs/`。

配置想让人改就写清楚：改哪个文件、哪个字段、改完怎么生效。不常见的组合与高级玩法不进 README。

## 设计与实现

技术选型表是可选的好形态：一行一项、选择与理由同表，比三段文字高效。项目用表格写选型时保持这个形态。

目录结构树只列到读者需要理解的那一层，每个目录一句用途。完整的层级与实现细节链到 `docs/`。

fork 或重写的项目必须有一节说明自己改了什么。只写「基于某项目的重写」不写差异，读者无法判断要不要用这个 fork。

## 文档

到仓库文档的索引，一行一条：文档名加一句话说它是什么。链接目标写相对路径。

README 只放索引，不放正文。过程性内容进项目文档，README 链过去。

## 许可证

一节或一句都行。许可证有附加条件的（第三方资源、商标、非公开部分不适用），一段写清哪些内容适用、哪些不适用，链到 NOTICE 或专项文档。只放一行链接解决不了权属混合的仓库。

## 内容边界

README 与其他文档的分工。写之前先想清楚这句话该不该出现在 README：

| 内容 | 放哪 |
| --- | --- |
| 这是什么、解决什么问题、怎么开始 | README |
| 截图、图标、特性清单 | README |
| 构建与使用需要的稳定事实（命令、配置、兼容范围） | README 或 `docs/`，链接互通 |
| 设计文档、验收记录、兼容边界详解 | `docs/` 专项文档 |
| 进度、交接、下一步、当前主线 | `docs/STATUS.md` 或 `docs/handoff/` |
| 本机路径、凭据位置、设备信息 | 不入库的项目约定文件 |

两个方向都错过：README 塞满过程细节，读者在更新记录里找安装命令。反过来只空三行，进度文档里的关键约定外人又看不到。判断标准：README 只回答第一次见面的问题，过程性记录交给项目文档。

README 不写「最近更新了什么」。那属于 Release 或交接记录，写在 README 迟早过期。

## 结构体检清单

写完或改完 README，过一遍：

- [ ] 图标有（有图标的项目），标题与图标位置固定、宽度合理
- [ ] 定位语两三句，没有会过时的动态
- [ ] 截图区在前半段，一到四张，不在表格里、同组同宽，没有逐图说明文字
- [ ] 快速开始只含实际用的那套命令，每条有上下文，环境变量有出处
- [ ] 每一节删掉会让读者卡住的才保留，凑数的已删
- [ ] 会过时的内容（版本动态、当前主线、最近更新）不在 README，链出去了
- [ ] 文件名是 `README.md`，全小写
- [ ] 全文一种语言
- [ ] 链接的目标文件都真实存在
- [ ] 句子与排版过了 chinese-tech-writing 的三个扫描脚本

## 改既有 README

1. 通读全文，列出问题清单：缺什么节、哪里凌乱、哪里过时。
2. 项目还有进度文档与项目文档时，先读它们，确认要迁出的内容有地方可去。
3. 用户只要意见时，按「现状 → 问题 → 改法」汇报，不动文件。
4. 确认后重写或修补，改完跑体检清单。
5. 有截图与图标的整改需求时（例如把逐图说明改成纯图排列），图片文件准备好再动结构，正文先改文字部分。
